# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Bun workspace (`apps/*`) plus a Cargo workspace (`crates/sush-core`, `apps/desktop/src-tauri`).

```sh
bun install
bun run dev              # auth server + Ollama + desktop app together
bun run dev:app          # desktop app only (tauri dev, Vite on fixed port 1420)
bun run dev:server       # auth server only, http://localhost:3000
bun run dev:relay        # the same server on every interface, as the LAN relay for shared sessions
bun run typecheck        # tsc in every workspace
bun --filter desktop build   # tsc + vite build (CI runs this)
bun run build            # compile auth sidecar + release installers

cargo test --workspace                       # what CI runs (Linux/Windows/macOS)
cargo test -p sush-core                      # core only
cargo test -p sush-core <name_substring>     # single test
cargo run -p sush-core --example chat -- <openai|anthropic> <base_url> <model> "prompt"   # SUSH_API_KEY for the key
```

There are no JS tests or linter configured; `typecheck` is the TS gate. Rust tests are inline `#[cfg(test)]` modules (decoders are tested against recorded SSE streams).

Building the Tauri crate needs CMake + libclang (whisper.cpp via `whisper-rs`). On Windows, set `CMAKE` / `LIBCLANG_PATH` if they aren't on PATH (see README).

Releases: main always carries the version it will be released as. Every push to main runs `.github/workflows/build.yml` (signed installers for every platform, kept on the run); pushing a `v*` tag on a main commit runs `release.yml`, which compiles nothing and publishes that commit's installers with `latest.json` (draft, attach, publish). The `release` skill tags, then bumps main to the next version.

## Architecture

Four parts:

- **`crates/sush-core`**: pure Rust, no Tauri dependency (keep it that way; it is meant to back a future CLI/TUI too). Holds the message model (`message.rs`: `Message`, `Part`, `ChatEvent`, `ChatRequest`), the `Provider` trait, SSE parsing, MCP client (`mcp/`: stdio + HTTP transports and OAuth), remote transcription, image generation (`imagegen.rs`: `/images/generations` or chat with image output), local persistence (`store.rs`, `memory.rs`), the agent loop (`agent/`), and Cowork workspaces (`workspace/`).
  - `agent/run.rs`: one run on a thread: stream a model step, resolve its tool calls (`Approval::Auto` ones run, `Ask` ones wait for the user, so the run reports `Awaiting`), repeat; saves at step boundaries. A message sent mid-run (`Steer`) joins at the next step boundary (the UI queues it until then), or at once on "Send now" (`Inbox::Interrupt`, via `run_interrupt`: the step or tool calls in progress end early, cut-short calls get an `INTERRUPTED` result, and the run carries on); a stop marks the reply `paused` and `Resume` carries on from it; `Inbox::Pause` is the gentle stop (the step and running tool calls finish, then the run ends `paused` at the boundary, calls waiting for approval left waiting). App specifics come through the `RunHost` trait. Tests drive it with a scripted fake host.
  - `agent/deferred.rs`: tools loaded on demand. A `RunTool` with `deferred` stays out of requests until the model calls `tools_load` (listed in the system prompt by name and first sentence; what's loaded is read from the thread's earlier `tools_load` calls). The UI defers its specialised tools (`DEFERRED` in `lib/agent.ts`) and every connector not @-mentioned; plain chats defer `spawn_agent`. Prompt caching depends on the prefix staying put: keep the system prompt free of per-request values (times, ids), and the tool list in a stable order. Anthropic requests carry `cache_control` marks (system prompt, end of conversation); OpenAI caches by itself. Usage metadata: `inputTokens` is billed input summed over a reply's steps, `contextTokens` the last step's, `cachedInputTokens` and `steps` alongside.
  - `agent/subagents.rs`: the `spawn_agent` tool. A run hands a self-contained task to a sub-agent: a run of its own on a child thread (`ThreadMeta.parent_id`, id `<parent>:<call id>`) with the parent's tools and folder, sub-agent instructions and no `spawn_agent` (no nesting); the call's result is the child's final message (`final_text`). Several calls in one step run in parallel like any tool calls. A sub-agent can work in the background (`background: true`, or moved there when the user sends a message while it works: `RunHost::detach`, so steers and "Send now" never wait for or cut short sub-agents): its call returns at once and its report later reaches the parent as a user message with `metadata.subagentReport` (`report_message`), joining the parent's run or starting one. Child threads are kept out of the session list and search and deleted with their parent.
  - `agent/ui.rs`: threads are kept as the UI's own message JSON (AI SDK `UIMessage`). Runs change them only through `Op`s, which the UI applies identically (`applyOp` in `sessions.ts`); also `to_core` (UI messages → provider `Message`s), the step builder (`ChatEvent`s → parts), citations and titles.
  - `workspace/`: Cowork's file and shell tools. All file access goes through a `cap_std::fs::Dir` on the granted folder, so `..`, absolute paths and escaping symlinks fail; `.git` and `.sush` are read-only; secret-looking files (`.env`, keys) need approval to read. `tools.rs` holds the tool specs, the per-call approval rule (edits and commands ask unless the workspace is set to `auto-edits`) and the dispatcher, which checkpoints a file before changing it. In a git repo it adds `branch_status` (the pull request card), `git_commit` and `git_merge` (`git.rs`): they write `.git`, which the file tools and the sandbox can't, run with the folder's hooks disabled, and checkpoint the files a merge changes; `git_merge` with `into` fast-forwards the base, possibly in the user's own checkout. `shell.rs` runs PowerShell on Windows and `sh` elsewhere with credential env vars removed, capped output, a timeout, and tree-kill on Stop.
    - `sandbox/`: commands run in an OS sandbox that confines writes to the workspace and a private temp folder (never `.git`): Seatbelt on macOS, bubblewrap on Linux (both also block the network), and on Windows a write-restricted token whose capability SID is granted (by ACL) the workspace folder, inside a Job Object; Windows can't block the network without admin. A self-test probe must pass before the sandbox counts as available (`SandboxStatus`). A workspace set to edit automatically runs every call without asking (commands with `network`/`unsandboxed`, pushes, `git_merge` with `into`) except `tools::destructive` commands (sudo, force-push or remote delete, `reset --hard`/`clean`, deletes outside the folder, a download piped into a shell) and secret-looking reads; one set to ask asks for every edit and command. A workspace can instead run commands on the user's machine (`Workspace.commands`: `sandbox` or `desktop`, the folder chip's "Commands run"), so servers can listen and installs reach the network; there `tools::contained` is false, which shared sessions use to floor approvals.
  - `reports.rs`: security reviews, code reviews and codebase wikis ("reports") of a workspace, stored in `sush.db` (`reports` table, the whole report as JSON). Each runs as an ordinary agent run on a thread of its own (a wiki also has a question thread); the host holds such a thread to reading (folder forced read-only, no browser, none of the UI's tools except a pull request review's connector tools) and gives it `git_diff` and the tool that records results (`report_findings`, `wiki_write_page`). Fixes go through a normal Cowork session.
  - `share/`: live shared sessions (see `docs/multiplayer-plan.md`). The host is authoritative: guests get a thread as the same `Op`s the UI applies, after `redact`, and send only `Intent`s, which `policy::authorize` checks (deny by default, secret paths never, owner actions never from the network). Read the `multiplayer` skill before changing anything here.
  - `engines/`: a Cowork session run by the user's own Claude Code (`claude -p`, stream-json) or Codex (`codex app-server`, JSON-RPC) instead of `agent::run`, picked as the provider ids `engine:claude-code` / `engine:codex` (`engines_list` adds them to the model picker when installed). Same contract as `agent::run`: same `Op`s, inbox and statuses; the CLI's permission prompts become Sush's approval cards and its tools Sush's cards where one fits (`claude_tool`, `codex::item`); its session id rides on each reply (`metadata.engineSession`). The user signs in inside the CLI, never in Sush: read `docs/engines.md` (the providers' terms) before changing how an engine starts or authenticates. `runs.rs` routes to it (`prepare_engine`: Cowork only, no Sush tools).
  - `web.rs`: the `web_search` / `web_fetch` tools (UI-owned, `lib/web.ts`, on by default via `prefs.webSearch`, Settings → Search; the model decides when to search). Search goes through Ollama's web search API with the user's Ollama key (`secrets::web_key_*`, else an `ollama.com` provider's key, `src-tauri/src/web.rs`); a page is read through Ollama with a key, else fetched from this machine, public addresses only (checked every redirect, pinned with `resolve`). Anthropic and OpenAI Responses requests swap these specs for the provider's own search by name (`request_body_with(req, native_web)`), go again with Sush's tools if the host refuses them, and keep Sush's tools when the thread already called them (`web::native_ok`). Research is now the "search harder" system section (`RESEARCH_SECTION`) and still adds Anthropic's tools.
  - A provider is *wire format × endpoint × credential*. Only two wire formats exist as provider settings (`OpenaiChat`, `AnthropicMessages` in `providers/`), and `OpenaiChat` sends the GPT-5.6 and GPT-6 models to the Responses API by itself (`providers/openai_responses.rs`), since they can't reason and call tools on Chat Completions; Azure, OpenRouter, Groq, Ollama, etc. are just `ProviderConfig` presets (`provider.rs::presets`). A new endpoint speaking an existing format needs config, not code.
  - Each format implements an I/O-free `Decoder` that turns SSE events into normalised `ChatEvent`s. Dropping the returned stream aborts the HTTP request; that is the cancellation mechanism.
- **`apps/desktop/src-tauri`** (crate `sush`): thin shell exposing core to the UI as Tauri commands (registered in `lib.rs`). `AppState` (`state.rs`) holds providers (persisted to `providers.json` in the app config dir), the store, memory, live runs, and cancellation tokens for one-shot streams and sign-ins. `runs.rs` is the session manager: one live run per thread, every run's frames on one channel (`runs_subscribe`, which also returns live runs so a reloaded page catches up), connector tools called from Rust, UI-owned tools requested with a `client-tool` frame and answered with `tool_result`. For a Cowork session (`ThreadMeta.workspace_id`), `runs.rs` adds the workspace tools itself (any the UI sends are dropped), decides each call's approval (`RunHost::approval`), and records checkpoints for undo. A thread that belongs to a report (`sush_core::reports`) gets `report_config` instead: read-only, with the report's own tools (`ToolExec::Report`) and instructions; a run's start and end set the report's status, and every change reaches all windows as a `report` frame. `spawn_agent` (`ToolExec::Agent`) is added in `prepare` for every session thread that isn't incognito, a report or itself a sub-agent; `Host::spawn_agent` starts the child run with the parent's pre-`prepare` config (`Live.ui_config`) and waits for it, stopping it if the call is cancelled, and the child checkpoints its edits under the parent's thread and turn (`Live.checkpoint_to`) so the parent turn's undo covers them. `agent_spawn` starts one from the graph's "Add an agent" (always in the background, call id `added-<first call of the graph>-<time>`), through the same `start_agent`. `thread_rewind` restores a checkpoint: it stops the run, puts back the files changed from a user message's turn on (`workspaces::restore_since`, shared with `undo_turn`), cuts the thread to before that message, and sends every window a `reset`. `reports.rs` holds the report commands (create, rerun, set a wiki's question thread, delete). `browser.rs` is Cowork's built-in browser: one native child webview (needs tauri's `unstable` feature) laid over the panel at the bounds the UI reports, driven by the `sush_core::browser` tools through `eval_with_callback`; pages get no IPC, and the app's own origins are refused. `workspaces.rs` adds workspaces through a folder dialog opened in Rust (the webview never names a path), and serves the file tree, file viewer and editor (`workspace_read_file`, `workspace_find`, `workspace_write_file` for the user's own saves, `workspace_reveal`), `sandbox_status`, `turn_diff` (each file a turn changed, before and after, from its checkpoints) and `undo_turn` (a whole turn, or one file). `terminal.rs` is the side panel's terminal: the user's own shell (PowerShell on Windows) in the workspace over plain pipes, not a PTY, and not sandboxed. Each command is wrapped so a marker line carrying the shell's cwd follows it (the UI's prompt); Stop kills the shell's tree and restarts it in that cwd. Likewise `pick_folder_attachment` and `save_text_file_as` open their dialogs in Rust. API keys and connector tokens go to the OS keyring (`secrets.rs`), never to disk or the webview. Debug builds instead keep them in an owner-only `dev-secrets.json` in the app config dir, because each `tauri dev` rebuild is re-signed and macOS would otherwise ask for the keychain password on every launch. `windows.rs` is the browser-style tab tear-off: `tab_drop` moves a tab dragged out of the strip into another window's strip (by cursor position) or into a new `session-*` window running the same page, and `tab_hover` has the strip under the cursor open a slot for it during the drag; each window subscribes to runs (frames go to all of them; `client-tool` frames only to the leader, `main` while it's open) and the browser webview moves to whichever window shows its pane. `share.rs` is shared sessions over the relay (both WebSocket ends in Rust, end-to-end encrypted); how it works is in the `multiplayer` skill. `paths.rs`: debug builds with `SUSH_PROFILE=b` use their own data/config dirs (and WebView2 storage on Windows) so two instances on one machine act as two people. `login_env.rs` (macOS, Linux) puts the user's login-shell PATH first at startup, before anything else runs, since an app opened from Finder or a launcher gets only the system PATH and Cowork commands, the terminal and the sandbox wouldn't find `bun`, Homebrew or nvm; skipped when started from a terminal. `yammer.rs` makes Yammer (Sush's dictation app, `../sush-voice`) the default dictation: it finds the installed app, reads its `settings.json` (`onboarded`, `hotkey`), and toggles it with `yammer --toggle`, which its single-instance plugin forwards to the running instance; a cold start with `--toggle` doesn't dictate, so a stopped Yammer is launched `--hidden` first (through `open` on macOS, so its permissions stay its own) and toggled after a grace period. Yammer pastes at the cursor, so the composer keeps focus (`useDictation`'s `focus`); `components/yammer-setup-dialog.tsx` guides installing and setting it up, and Settings → Speech switches to Sush's own (`SpeechSettings.engine`, missing means Yammer). `whisper.rs` runs Sush's own local dictation in-process (model downloaded on first use). `images.rs` generates an image with the provider/model picked in Settings → Images and stores it as a blob. `auth_server.rs` is release-only (`#[cfg(not(debug_assertions))]`): it launches the bundled auth server sidecar on port 47321 with a per-install secret it generates into the app data dir (`auth-secret`); no secret is baked into the binary. The sidecar is also the installed app's relay: Settings → Sharing's "Let others on this Wi-Fi join" (`share::local_relay_set_lan`, remembered as `relay-lan` in the app data dir) restarts it with `SUSH_RELAY_LAN`, and it serves the browser viewer bundled as a resource (`viewer/`, built by `build:viewer` in the build scripts and `release.yml`). In dev you run `dev:server` yourself.
- **`apps/desktop/src`**: React 19 + Vite + Tailwind 4 + shadcn (`components/ui`) + AI SDK UI (`useChat`). Path alias `@/` → `src/`.
  - `lib/tauri.ts`: typed `invoke` bindings. Its types mirror sush-core's serde shapes (camelCase fields, kebab-case enum tags). **If you change a Rust command or serde type, update this file to match.**
  - `lib/transport.ts`: the chat message types (`SushUIMessage`) and `storeAttachments`. `chat_stream` remains only for one-shot calls (`lib/complete.ts`: titles, memory revision).
  - `lib/agent.ts`: what each request carries (system prompt, tool specs via `buildContext`), each tool's approval policy (`runTools`), and `runTool` for the tools the UI owns (`memory_*`, `chats_search`/`chat_read`, `skill`, `artifact_write`, `image_generate`, `map_show`, `flights_search`, `topic_lookup`, `weather_show` and `todo_write` (`lib/todos.ts`: the model's to-do list for a multi-step task, always offered with standing instructions in the system prompt; the latest list in a reply stays in view as a checklist, earlier ones fold into the activity line, and `components/plan-tray.tsx` docks the current one on the composer while it runs; in Cowork the loop also nudges, `sush_core::agent::plan`: a reminder on the turn's first request, and a `planCheck` message sending the model back once a turn if it ends with items left): how each works (cards, keys in the keyring, keyless fallbacks) is in the `add-agent-tool` skill; images they show need their hosts in `img-src` in the CSP, and a tool output's `cardOnly` field stays in the thread but is stripped before the model (`CARD_ONLY` in `agent/ui.rs`)). `ask_user` (choices, or `type` date / date-range: a calendar in `components/date-question.tsx`, also shown for choices that are nearly all dates, typed dates read by `lib/dates.ts`, answers as `YYYY-MM-DD`; a flight's dates also ask travelers and class, answered as `travel`), `skill_save` and `location_get` (`lib/location.ts`: the saved address from Settings → Maps or the device's position (on macOS through CoreLocation, `location_read` in `src-tauri/src/location.rs`, because WKWebView refuses `navigator.geolocation`), asked for on every call; a device position shared "for this session" is removed from the stored chats on quit and at launch, `Store::forget_session_locations`) are answered in their cards; `location_get`, `map_show`, `flights_search` and `weather_show` are hidden from shared-session guests; tools named `<connector>__<tool>` run in Rust after approval unless allowed.
  - Swiggy Food and Instamart are ordinary connectors with their own cards; see the `swiggy` skill. Any connector tool that spends money (`places_order` in `share/policy.rs`, `placesOrder` in `connector-catalog.ts`; keep them in step) always asks, ignores "Always allow", and only the owner answers it.
  - Conversations and memory are stored on disk by Rust and loaded once at startup (`initStore` / `initMemory`, awaited in `main.tsx`). `lib/store.ts` and `lib/memory.ts` keep an in-memory copy for synchronous reads and write every change through to Rust in order. Keep UI code going through those modules' APIs. Conversations live in `sush.db` (`sush_core::store`: SQLite + FTS5 for `chats_search`); images and PDFs are content-addressed files in `blobs/`, served to the webview on the `sushblob` scheme and resolved to base64 in `chat_stream`; memory files are markdown in `memory/` (`sush_core::memory`), all under the app data dir. The library (`library.ts`: skills, design systems, connectors, plugins) and preferences still use localStorage via `createStore`.
  - `lib/workspaces.ts`: the workspace list, `CurrentWorkspace` (context for tool cards), file-change versions from `files-changed` frames, and undo. `components/workspace-panel.tsx` holds the header's folder chip (mode, sandbox status) and panel toggles, and the side panel: lazy file tree with a filter and context menus, tabs, the editable viewer (`components/code-editor.tsx`: a transparent textarea over shiki output, unsaved text in the drafts store in `workspaces.ts`, Ctrl+S saves), and the terminal (`components/terminal-pane.tsx`, no terminal emulator, drawn with the parts exported from `components/ui/Terminal.tsx`) below a draggable split. In a git repo a Graph toggle adds `components/git-graph-pane.tsx`: the history in lanes (`workspace_git_log` → `git::log`, every branch or only the current one; lane layout shared with the branch card in `lib/commit-graph.ts`), with a picked commit's message and files below (`workspace_git_commit`); it re-reads as files change, and each terminal command finishing counts as a change. Under each Cowork turn, `components/file-changes.tsx` lists the files it changed with +/− counts, a diff and per-file Undo. The Chat / Cowork toggle in the sidebar's title bar switches the open session's kind (Cowork reopens the most recently used folder), and "New" starts the same kind as the open one. A new session's composer has `components/session-options.tsx` above it (switch folder or plain chat while the session is untouched; in a git repo, a branch chip that switches branches via `workspace/git.rs` and a "worktree" checkbox: on the first send, `worktree_create` adds a worktree on a new `sush/…` branch under the app data dir as its own workspace and the session moves into it) and the mascot, Sushi (`components/mascot.tsx`), standing on it. The latest `branch_status` call renders as `components/branch-card.tsx`: a live commit graph of the branch against its base (`workspace_branch_status`, re-read as files change), conflicts from `git merge-tree` with their lines on hover, the checks and PR state the model passed, a button that sends the next step as a message, and a chip above the composer. Cowork tool calls render in `WorkspacePart` (`tool-parts.tsx`); finished tool calls and the thinking between them collapse into one line (`components/activity-group.tsx`).
  - Sub-agents: `components/subagents.tsx` renders each step's `spawn_agent` calls as one graph: the lead (the mascot picked in Settings) above a node per agent, each a different sushi (`Mascot` with `still`) acting out its stage, with work flowing along the connectors while it runs; clicking a node opens the child thread's work below (`useThread(<parent>:<call id>)`), where its approvals are answered, and it opens by itself when the agent needs input. `lib/store.ts` keeps child threads apart from the conversations (`getSubagentThread`).
  - The sidebar's Security, Review and Wiki pages (`components/reports-page.tsx`, `components/wiki-page.tsx`) run and show reports of a chosen workspace; `lib/reports.ts` starts them (creates the report, then sends the kickoff message on its thread), mirrors `report` frames, and broadcasts its own changes. Report threads are kept out of the session list (`useReportThreads`). A finding's "Fix" starts a normal Cowork session; file citations open in the Cowork file viewer at their line (`openFile(…, line)`).
  - Sessions can be renamed, forked, filed under a project (`lib/projects.ts`: name + instructions in localStorage; membership is `ThreadMeta.project_id`) via `components/session-actions.tsx`. The sidebar's Board (`components/board-page.tsx`, `lib/board.ts`): the user's tasks in localStorage (`sush.board.tasks`), shown as Kanban columns by priority (plus Completed) or by status, or as a list; cards drag with pointer events (Tauri takes HTML5 drag and drop on Windows); "Start session" opens Cowork in the task's folder (a chat without one) prefilled with the task and records the session on it (`linkSession`, which also moves a to-do task to in progress). Incognito chats (`ThreadMeta.incognito`) are never stored: `Store::save_thread` skips them, `runs.rs` keeps their messages in memory until `thread_delete`, they get no memory/past-chat tools and no workspace, and `App.tsx` deletes one when you leave it.
  - Several windows: each keeps its own in-memory copy of the store, so `lib/windows.ts` broadcasts changes between them (conversations, memory, the workspace list), persisted `createStore`s follow other windows' writes via the `storage` event (pass `follow = false` for per-window state like the tab strip and Cowork panels), and `whenLeader` runs once-only work (automations). New code that changes shared state in memory needs to broadcast it too.
  - `lib/share.ts`: shared sessions in the UI; it mirrors `share` frames (Rust owns the state). Its components, and how a guest's actions become intents, are in the `multiplayer` skill.
  - Updates and release notes: `lib/updater.ts` checks the release feed (sidebar "Upgrade now"); `lib/changelog.ts` holds the user-facing notes (`RELEASED`, newest first, plus `UNRELEASED` and `UNRELEASED_SUMMARY`: the notes of the version main is building, shown as that version's entry, dated by the build via `__APP_VERSION__`/`__BUILD_DATE__` from `vite.config.ts`; `CHANGELOG` is both) and opens `WhatsNewDialog` (`components/changelog.tsx`) once after an update moves past the last version seen (`sush.changelog-seen`; a fresh install only records its version). Settings → What's new shows every release up to the installed one. Add a line to `UNRELEASED` when a user-visible feature lands; it ships in the next tagged build, and the `release` skill then moves it into `RELEASED`.
  - `lib/sessions.ts`: starts, answers (`respond`) and stops runs, builds each run's `RunConfig` (including `/skill` and `@connector` expansions), and mirrors every thread's messages from the run frames. `ChatView` reads a thread with `useThread`; there is no `useChat`.
- **`apps/server`**: Bun + Hono + better-auth (SQLite, migrated on startup). Email/password accounts. It is also the relay for shared sessions (`src/share/`): REST for shares, invites (only a token hash is stored, and tokens travel in bodies, never paths; each is "to watch" or "to suggest", its `roleCap`, which the host learns on `peer-joined`) and members, plus a WebSocket room per share that forwards bodies without reading them, stamps the sender from the session, keeps guests in a lobby until the host admits them, and rate-limits guests (frames up to 8 MB, for images). It binds to 127.0.0.1 unless `SUSH_RELAY_LAN` is set (`bun run dev:relay`), which serves the LAN. `share/plans.ts` is the seat and plan hooks (off unless `SUSH_PLANS=on`; `GET /api/shares/limits`), and `share/metrics.ts` the opt-in weekly usage counts (no ids, no content; `GET /api/metrics/weekly` for `SUSH_ADMIN_EMAILS`). At an invite link's own address (`/join/:id`) it serves the browser viewer. The webview is cross-origin, so auth uses the bearer plugin (`set-auth-token` header → localStorage → `Authorization: Bearer`, see `src/lib/auth.ts`) instead of cookies. In release builds it is compiled with `bun build --compile` into `src-tauri/binaries/sush-auth-<target-triple>` and shipped as a Tauri sidecar.

- **`apps/viewer`**: the browser viewer for shared sessions (Vite + React, no Tauri): sign in to the relay with cookies, join from the link, wait in the lobby, then watch and comment. Its own replica (`session.ts`) and encryption (`crypto.ts`, `@noble`) mirror `sush_core::share`. Built with `base: "/viewer/"` into `dist`, which the relay serves (`bun run build:viewer`; `bun run dev:viewer` proxies the relay on 3000).

`apps/chat-ui.tsx` is a standalone component file outside every workspace package; nothing imports it.

Project skills in `.claude/skills/` cover the common multi-file workflows: `check`, `ship`, `run-app`, `add-tauri-command`, `add-agent-tool`, `add-provider`, `multiplayer` (shared sessions: protocol, intents, the next phases, testing with two instances), `swiggy` (Food and Instamart connectors, their cards and order safety), `release`, `build-dmg`.

## Gotchas

- Don't build, test, or typecheck after making changes (no `bun run typecheck`, `bun --filter desktop build`, `cargo build/check/test`, `tauri build`). Builds run only when the user asks, once a feature is complete and right before pushing: that's the `/ship` skill (or `/check` to verify without pushing).
- The CSP in `tauri.conf.json` (and `tauri.release.conf.json` for release) restricts `connect-src`. If you point `VITE_AUTH_URL` at a new origin, or the webview needs to reach a new host, add it there.
- Server env: `BETTER_AUTH_SECRET` (required in production), `BETTER_AUTH_URL`, `PORT`, `DATABASE_PATH`.
- macOS app icon: on macOS 26 the icon follows light/dark and the Clear/Tinted styles through `icons/Assets.car`, compiled from `icons/AppIcon.icon` by Xcode's `actool`. Never install Xcode for it: `.github/workflows/mac-icon.yml` compiles it on GitHub and commits it with `Assets.car.stamp` whenever the icon changes. `tauri.macos-icon.conf.json` (passed by `build:mac` and `release.yml`) bundles it and runs `icons/check-mac-icon.sh` before bundling, which stops the build when the stamp doesn't match the current `AppIcon.icon`. So after an icon change, push, let the workflow commit, and pull before building a DMG. Don't edit `Assets.car.stamp` by hand.
