# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Bun workspace (`apps/*`) plus a Cargo workspace (`crates/sush-core`, `apps/desktop/src-tauri`).

```sh
bun install
bun run dev              # auth server + Ollama + desktop app together
bun run dev:app          # desktop app only (tauri dev, Vite on fixed port 1420)
bun run dev:server       # auth server only, http://localhost:3000
bun run dev:relay        # the same server on every interface, as the LAN relay for shared sessions
bun run typecheck        # tsc in every workspace
bun --filter desktop build   # tsc + vite build (CI runs this)
bun run build            # compile auth sidecar + release installers

cargo test --workspace                       # what CI runs (Linux/Windows/macOS)
cargo test -p sush-core                      # core only
cargo test -p sush-core <name_substring>     # single test
cargo run -p sush-core --example chat -- <openai|anthropic> <base_url> <model> "prompt"   # SUSH_API_KEY for the key
```

There are no JS tests or linter configured; `typecheck` is the TS gate. Rust tests are inline `#[cfg(test)]` modules (decoders are tested against recorded SSE streams).

Building the Tauri crate needs CMake + libclang (whisper.cpp via `whisper-rs`). On Windows, set `CMAKE` / `LIBCLANG_PATH` if they aren't on PATH (see README).

Releases: push a `v*` tag matching the version in `tauri.conf.json`; `.github/workflows/release.yml` builds every platform.

## Architecture

Three parts:

- **`crates/sush-core`**: pure Rust, no Tauri dependency (keep it that way; it is meant to back a future CLI/TUI too). Holds the message model (`message.rs`: `Message`, `Part`, `ChatEvent`, `ChatRequest`), the `Provider` trait, SSE parsing, MCP client (`mcp/`: stdio + HTTP transports and OAuth), remote transcription, image generation (`imagegen.rs`: `/images/generations` or chat with image output), local persistence (`store.rs`, `memory.rs`), the agent loop (`agent/`), and Cowork workspaces (`workspace/`).
  - `agent/run.rs`: one run on a thread: stream a model step, resolve its tool calls (`Approval::Auto` ones run, `Ask` ones wait for the user, so the run reports `Awaiting`), repeat; saves at step boundaries. A message sent mid-run (`Steer`) joins at the next step boundary (the UI queues it until then), or at once on "Send now" (`Inbox::Interrupt`, via `run_interrupt`: the step or tool calls in progress end early, cut-short calls get an `INTERRUPTED` result, and the run carries on); a stop marks the reply `paused` and `Resume` carries on from it. App specifics come through the `RunHost` trait. Tests drive it with a scripted fake host.
  - `agent/subagents.rs`: the `spawn_agent` tool. A run hands a self-contained task to a sub-agent: a run of its own on a child thread (`ThreadMeta.parent_id`, id `<parent>:<call id>`) with the parent's tools and folder, sub-agent instructions and no `spawn_agent` (no nesting); the call's result is the child's final message (`final_text`). Several calls in one step run in parallel like any tool calls. A sub-agent can work in the background (`background: true`, or moved there when the user sends a message while it works: `RunHost::detach`, so steers and "Send now" never wait for or cut short sub-agents): its call returns at once and its report later reaches the parent as a user message with `metadata.subagentReport` (`report_message`), joining the parent's run or starting one. Child threads are kept out of the session list and search and deleted with their parent.
  - `agent/ui.rs`: threads are kept as the UI's own message JSON (AI SDK `UIMessage`). Runs change them only through `Op`s, which the UI applies identically (`applyOp` in `sessions.ts`); also `to_core` (UI messages → provider `Message`s), the step builder (`ChatEvent`s → parts), citations and titles.
  - `workspace/`: Cowork's file and shell tools. All file access goes through a `cap_std::fs::Dir` on the granted folder, so `..`, absolute paths and escaping symlinks fail; `.git` and `.sush` are read-only; secret-looking files (`.env`, keys) need approval to read. `tools.rs` holds the tool specs, the per-call approval rule (shell always asks; edits ask unless the workspace is set to `auto-edits`) and the dispatcher, which checkpoints a file before changing it. In a git repo it adds `branch_status` (the pull request card), `git_commit` and `git_merge` (`git.rs`): they write `.git`, which the file tools and the sandbox can't, run with the folder's hooks disabled, and checkpoint the files a merge changes; `git_merge` with `into` (fast-forward the base, possibly in the user's own checkout) always asks. `shell.rs` runs PowerShell on Windows and `sh` elsewhere with credential env vars removed, capped output, a timeout, and tree-kill on Stop.
    - `sandbox/`: commands run in an OS sandbox that confines writes to the workspace and a private temp folder (never `.git`): Seatbelt on macOS, bubblewrap on Linux (both also block the network), and on Windows a write-restricted token whose capability SID is granted (by ACL) the workspace folder, inside a Job Object; Windows can't block the network without admin. A self-test probe must pass before the sandbox counts as available (`SandboxStatus`). Shell commands run without asking only when the sandbox is available, blocks the network, the command doesn't request `network`/`unsandboxed`, and the workspace is set to edit automatically; otherwise they ask.
  - `reports.rs`: security reviews, code reviews and codebase wikis ("reports") of a workspace, stored in `sush.db` (`reports` table, the whole report as JSON). Each runs as an ordinary agent run on a thread of its own (a wiki also has a question thread); the host holds such a thread to reading (folder forced read-only, no browser, none of the UI's tools except a pull request review's connector tools) and gives it `git_diff` and the tool that records results (`report_findings`, `wiki_write_page`). Fixes go through a normal Cowork session.
  - `share/`: live shared sessions (see `docs/multiplayer-plan.md`). The host is authoritative: guests get a thread as the same `Op`s the UI applies, after `redact` (private tools' input and output, secret files' content, credential-looking text in tool output), and send only `Intent`s, which `policy::authorize` checks against the sender's role and what the session shows (deny by default, secret paths never, owner actions never from the network). Roles: a viewer reads; a collaborator's message becomes a `Suggestion` (and they comment); the one driver steers, stops, resumes, "Send now"s and answers the approvals `policy::may_answer` allows (questions, plus the `Delegation` the owner set; secret reads never). `policy::classify` gives each call an `ApprovalClass`, and `floored` says which ones ask again while others can steer. `audit` is the log's entry type (`share_events` in the store). `outbox` numbers the host's messages (`epoch`/`seq`) and merges text deltas. `replica` is a guest's copy, which asks for a snapshot on any gap. Message bodies are versioned (`v`). The relay never reads them. Who answered a tool call is recorded by the runner itself (`RunAction::Respond { by }` → `metadata.sushAnswers`), where it already decides first-wins.
  - A provider is *wire format × endpoint × credential*. Only two wire formats exist (`OpenaiChat`, `AnthropicMessages` in `providers/`); Azure, OpenRouter, Groq, Ollama, etc. are just `ProviderConfig` presets (`provider.rs::presets`). A new endpoint speaking an existing format needs config, not code.
  - Each format implements an I/O-free `Decoder` that turns SSE events into normalised `ChatEvent`s. Dropping the returned stream aborts the HTTP request; that is the cancellation mechanism.
- **`apps/desktop/src-tauri`** (crate `sush`): thin shell exposing core to the UI as Tauri commands (registered in `lib.rs`). `AppState` (`state.rs`) holds providers (persisted to `providers.json` in the app config dir), the store, memory, live runs, and cancellation tokens for one-shot streams and sign-ins. `runs.rs` is the session manager: one live run per thread, every run's frames on one channel (`runs_subscribe`, which also returns live runs so a reloaded page catches up), connector tools called from Rust, UI-owned tools requested with a `client-tool` frame and answered with `tool_result`. For a Cowork session (`ThreadMeta.workspace_id`), `runs.rs` adds the workspace tools itself (any the UI sends are dropped), decides each call's approval (`RunHost::approval`), and records checkpoints for undo. A thread that belongs to a report (`sush_core::reports`) gets `report_config` instead: read-only, with the report's own tools (`ToolExec::Report`) and instructions; a run's start and end set the report's status, and every change reaches all windows as a `report` frame. `spawn_agent` (`ToolExec::Agent`) is added in `prepare` for every session thread that isn't incognito, a report or itself a sub-agent; `Host::spawn_agent` starts the child run with the parent's pre-`prepare` config (`Live.ui_config`) and waits for it, stopping it if the call is cancelled, and the child checkpoints its edits under the parent's thread and turn (`Live.checkpoint_to`) so the parent turn's undo covers them. `agent_spawn` starts one from the graph's "Add an agent" (always in the background, call id `added-<first call of the graph>-<time>`), through the same `start_agent`. `thread_rewind` restores a checkpoint: it stops the run, puts back the files changed from a user message's turn on (`workspaces::restore_since`, shared with `undo_turn`), cuts the thread to before that message, and sends every window a `reset`. `reports.rs` holds the report commands (create, rerun, set a wiki's question thread, delete). `browser.rs` is Cowork's built-in browser: one native child webview (needs tauri's `unstable` feature) laid over the panel at the bounds the UI reports, driven by the `sush_core::browser` tools through `eval_with_callback`; pages get no IPC, and the app's own origins are refused. `workspaces.rs` adds workspaces through a folder dialog opened in Rust (the webview never names a path), and serves the file tree, file viewer and editor (`workspace_read_file`, `workspace_find`, `workspace_write_file` for the user's own saves, `workspace_reveal`), `sandbox_status`, `turn_diff` (each file a turn changed, before and after, from its checkpoints) and `undo_turn` (a whole turn, or one file). `terminal.rs` is the side panel's terminal: the user's own shell (PowerShell on Windows) in the workspace over plain pipes, not a PTY, and not sandboxed. Each command is wrapped so a marker line carrying the shell's cwd follows it (the UI's prompt); Stop kills the shell's tree and restarts it in that cwd. Likewise `pick_folder_attachment` and `save_text_file_as` open their dialogs in Rust. API keys and connector tokens go to the OS keyring (`secrets.rs`), never to disk or the webview. Debug builds instead keep them in an owner-only `dev-secrets.json` in the app config dir, because each `tauri dev` rebuild is re-signed and macOS would otherwise ask for the keychain password on every launch. `windows.rs` is the browser-style tab tear-off: `tab_drop` moves a tab dragged out of the strip into another window's strip (by cursor position) or into a new `session-*` window running the same page, and `tab_hover` has the strip under the cursor open a slot for it during the drag; each window subscribes to runs (frames go to all of them; `client-tool` frames only to the leader, `main` while it's open) and the browser webview moves to whichever window shows its pane. `share.rs` is shared sessions over the relay (`apps/server` `/api/shares`). Both ends of the WebSocket are in Rust (`tokio-tungstenite`, bearer on the upgrade). The relay account (URL + token) is in the keyring (`secrets::share_account_*`). Host: every frame passes `Runs.shares.on_frame` under the channels lock (from `Runs::send` and `Host::emit`), and the frames of a shared thread or its sub-agents go into that share's outbox. A guest's hello gets a snapshot taken in `Runs::with_family` (same lock), so it lines up with the next op. Intents run through the same code as the UI's commands (`workspaces::turn_diff_files`, `file_view`, the store's blobs, and `runs::start_run` / `Runs::interrupt` / `stop_with_agents` for a driver's steer, respond, resume, "Send now" and stop). A run a guest starts needs the UI's config: a `share-config` frame goes to the leader window (like `client-tool`), which answers `share_config_result` with `runConfig` (budgets apply). Guest messages are built on the host, credited in `metadata.author` (any author a guest claims never counts), and their images are checked and stored as blobs. While a driver or collaborator is in, `Host::approval` asks again for standing permissions (`Shares::steerable`); role changes send `Inbox::Recheck`. Answers are first-wins per call (`HostShare::claim`), the owner's own too (`run_start` → `claim_local`, credited to the owner). Owner-only commands: `share_set_role`, `share_set_policy` (browsing, delegation), `share_suggestion_accept` / `_drop`, `share_comment`. Everything goes in the audit log (`HostShare::record` → `share_events`). Guest: host messages go into a `Replica` and come out as ordinary `RunFrame`s for `shared:<share id>` (`…:<call id>` for sub-agents), never saved. `store::serve_blob` fetches a joined share's attachments from its host. `paths.rs`: debug builds with `SUSH_PROFILE=b` use their own data/config dirs (and WebView2 storage on Windows) so two instances on one machine act as two people. `whisper.rs` runs local dictation in-process (model downloaded on first use). `images.rs` generates an image with the provider/model picked in Settings → Images and stores it as a blob. `auth_server.rs` is release-only (`#[cfg(not(debug_assertions))]`): it launches the bundled auth server sidecar on port 47321 with a per-install secret it generates into the app data dir (`auth-secret`); no secret is baked into the binary. In dev you run `dev:server` yourself.
- **`apps/desktop/src`**: React 19 + Vite + Tailwind 4 + shadcn (`components/ui`) + AI SDK UI (`useChat`). Path alias `@/` → `src/`.
  - `lib/tauri.ts`: typed `invoke` bindings. Its types mirror sush-core's serde shapes (camelCase fields, kebab-case enum tags). **If you change a Rust command or serde type, update this file to match.**
  - `lib/transport.ts`: the chat message types (`SushUIMessage`) and `storeAttachments`. `chat_stream` remains only for one-shot calls (`lib/complete.ts`: titles, memory revision).
  - `lib/agent.ts`: what each request carries (system prompt, tool specs via `buildContext`), each tool's approval policy (`runTools`), and `runTool` for the tools the UI owns (`memory_*`, `chats_search`/`chat_read`, `skill`, `artifact_write`, `image_generate`: offered only once an image model is set in Settings → Images (`lib/images.ts`), shown with `components/ai-elements/image.tsx`). `ask_user` and `skill_save` are answered in their cards; tools named `<connector>__<tool>` run in Rust after approval unless allowed.
  - Conversations and memory are stored on disk by Rust and loaded once at startup (`initStore` / `initMemory`, awaited in `main.tsx`). `lib/store.ts` and `lib/memory.ts` keep an in-memory copy for synchronous reads and write every change through to Rust in order. Keep UI code going through those modules' APIs. Conversations live in `sush.db` (`sush_core::store`: SQLite + FTS5 for `chats_search`); images and PDFs are content-addressed files in `blobs/`, served to the webview on the `sushblob` scheme and resolved to base64 in `chat_stream`; memory files are markdown in `memory/` (`sush_core::memory`), all under the app data dir. The library (`library.ts`: skills, design systems, connectors, plugins) and preferences still use localStorage via `createStore`.
  - `lib/workspaces.ts`: the workspace list, `CurrentWorkspace` (context for tool cards), file-change versions from `files-changed` frames, and undo. `components/workspace-panel.tsx` holds the header's folder chip (mode, sandbox status) and panel toggles, and the side panel: lazy file tree with a filter and context menus, tabs, the editable viewer (`components/code-editor.tsx`: a transparent textarea over shiki output, unsaved text in the drafts store in `workspaces.ts`, Ctrl+S saves), and the terminal (`components/terminal-pane.tsx`, no terminal emulator, drawn with the parts exported from `components/ui/Terminal.tsx`) below a draggable split. In a git repo a Graph toggle adds `components/git-graph-pane.tsx`: the history in lanes (`workspace_git_log` → `git::log`, every branch or only the current one; lane layout shared with the branch card in `lib/commit-graph.ts`), with a picked commit's message and files below (`workspace_git_commit`); it re-reads as files change, and each terminal command finishing counts as a change. Under each Cowork turn, `components/file-changes.tsx` lists the files it changed with +/− counts, a diff and per-file Undo. The Chat / Cowork toggle in the sidebar's title bar switches the open session's kind (Cowork reopens the most recently used folder), and "New" starts the same kind as the open one. A new session's composer has `components/session-options.tsx` above it (switch folder or plain chat while the session is untouched; in a git repo, a branch chip that switches branches via `workspace/git.rs` and a "worktree" checkbox: on the first send, `worktree_create` adds a worktree on a new `sush/…` branch under the app data dir as its own workspace and the session moves into it) and the mascot, Sushi (`components/mascot.tsx`), standing on it. The latest `branch_status` call renders as `components/branch-card.tsx`: a live commit graph of the branch against its base (`workspace_branch_status`, re-read as files change), conflicts from `git merge-tree` with their lines on hover, the checks and PR state the model passed, a button that sends the next step as a message, and a chip above the composer. Cowork tool calls render in `WorkspacePart` (`tool-parts.tsx`); finished tool calls and the thinking between them collapse into one line (`components/activity-group.tsx`).
  - Sub-agents: `components/subagents.tsx` renders each step's `spawn_agent` calls as one graph: the lead (the mascot picked in Settings) above a node per agent, each a different sushi (`Mascot` with `still`) acting out its stage, with work flowing along the connectors while it runs; clicking a node opens the child thread's work below (`useThread(<parent>:<call id>)`), where its approvals are answered, and it opens by itself when the agent needs input. `lib/store.ts` keeps child threads apart from the conversations (`getSubagentThread`).
  - The sidebar's Security, Review and Wiki pages (`components/reports-page.tsx`, `components/wiki-page.tsx`) run and show reports of a chosen workspace; `lib/reports.ts` starts them (creates the report, then sends the kickoff message on its thread), mirrors `report` frames, and broadcasts its own changes. Report threads are kept out of the session list (`useReportThreads`). A finding's "Fix" starts a normal Cowork session; file citations open in the Cowork file viewer at their line (`openFile(…, line)`).
  - Sessions can be renamed, forked, filed under a project (`lib/projects.ts`: name + instructions in localStorage; membership is `ThreadMeta.project_id`) via `components/session-actions.tsx`. Incognito chats (`ThreadMeta.incognito`) are never stored: `Store::save_thread` skips them, `runs.rs` keeps their messages in memory until `thread_delete`, they get no memory/past-chat tools and no workspace, and `App.tsx` deletes one when you leave it.
  - Several windows: each keeps its own in-memory copy of the store, so `lib/windows.ts` broadcasts changes between them (conversations, memory, the workspace list), persisted `createStore`s follow other windows' writes via the `storage` event (pass `follow = false` for per-window state like the tab strip and Cowork panels), and `whenLeader` runs once-only work (automations). New code that changes shared state in memory needs to broadcast it too.
  - `lib/share.ts`: shared sessions. It mirrors `share` frames (Rust owns the state and every window gets the frames, so nothing is broadcast; a `ShareView` carries roles, suggestions, comments and the audit log), runs the share/join/admit/kick/role/delegation/suggestion/comment actions, holds the relay account, and decides which waiting cards a driver may answer (`mayAnswer`, mirroring `policy::classify`). `components/share-dialog.tsx` (Share live…, relay setup, roles, delegation, activity), `components/shared-sessions.tsx` (the sidebar's "Shared with you", join dialog, header presence, `GuestComposer` for a driver or collaborator, the viewer's bar), `components/suggestion-queue.tsx`, `components/share-activity.tsx` (comments and the log, from the header) and `components/shared-files-panel.tsx` are its UI. A joined share opens on the `shared` page in `ChatView` with `watching` set. In `sessions.ts`, a guest's send, respond, stop, resume and "Send now" on a `shared:` thread become intents (`share_request`); edit, regenerate and rewind stay no-ops. Tool cards read `WatchingHost` (`{ hostName, mayAnswer }`) to show "Waiting for … to approve" on the rest, and `metadata.sushAnswers` for "Approved by …".
  - `lib/sessions.ts`: starts, answers (`respond`) and stops runs, builds each run's `RunConfig` (including `/skill` and `@connector` expansions), and mirrors every thread's messages from the run frames. `ChatView` reads a thread with `useThread`; there is no `useChat`.
- **`apps/server`**: Bun + Hono + better-auth (SQLite, migrated on startup). Email/password accounts. It is also the relay for shared sessions (`src/share/`): REST for shares, invites (only a token hash is stored, and tokens travel in bodies, never paths; each is "to watch" or "to suggest", its `roleCap`, which the host learns on `peer-joined`) and members, plus a WebSocket room per share that forwards bodies without reading them, stamps the sender from the session, keeps guests in a lobby until the host admits them, and rate-limits guests (frames up to 8 MB, for images). It binds to 127.0.0.1 unless `SUSH_RELAY_LAN` is set (`bun run dev:relay`), which serves the LAN. The webview is cross-origin, so auth uses the bearer plugin (`set-auth-token` header → localStorage → `Authorization: Bearer`, see `src/lib/auth.ts`) instead of cookies. In release builds it is compiled with `bun build --compile` into `src-tauri/binaries/sush-auth-<target-triple>` and shipped as a Tauri sidecar.

`apps/chat-ui.tsx` is a standalone component file outside every workspace package; nothing imports it.

Project skills in `.claude/skills/` cover the common multi-file workflows: `check`, `ship`, `run-app`, `add-tauri-command`, `add-agent-tool`, `add-provider`, `multiplayer` (shared sessions: protocol, intents, the next phases, testing with two instances), `release`, `build-dmg`.

## Gotchas

- Don't build, test, or typecheck after making changes (no `bun run typecheck`, `bun --filter desktop build`, `cargo build/check/test`, `tauri build`). Builds run only when the user asks, once a feature is complete and right before pushing: that's the `/ship` skill (or `/check` to verify without pushing).
- The CSP in `tauri.conf.json` (and `tauri.release.conf.json` for release) restricts `connect-src`. If you point `VITE_AUTH_URL` at a new origin, or the webview needs to reach a new host, add it there.
- Server env: `BETTER_AUTH_SECRET` (required in production), `BETTER_AUTH_URL`, `PORT`, `DATABASE_PATH`.
- macOS app icon: on macOS 26 the icon follows light/dark and the Clear/Tinted styles through `icons/Assets.car`, compiled from `icons/AppIcon.icon` by Xcode's `actool`. Never install Xcode for it: `.github/workflows/mac-icon.yml` compiles it on GitHub and commits it with `Assets.car.stamp` whenever the icon changes. `tauri.macos-icon.conf.json` (passed by `build:mac` and `release.yml`) bundles it and runs `icons/check-mac-icon.sh` before bundling, which stops the build when the stamp doesn't match the current `AppIcon.icon`. So after an icon change, push, let the workflow commit, and pull before building a DMG. Don't edit `Assets.car.stamp` by hand.
